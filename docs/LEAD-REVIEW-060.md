# Независимое ревью Psalmony 0.6.0

Дата: 11 октября 2026 года. Объект: незакоммиченные изменения рабочего дерева, включая новые файлы. Проверка исходников и узкие воспроизведения в Node; производство этим ревью не изменялось. Окончательные проверки выпуска ведёт координатор.

## Решение

**Технический gate кода закрыт: подтверждённых открытых блокеров нет.** Оба первоначальных P1 исправлены, регрессии асинхронных ответов и финальные HTTP/БД проверки проходят. Дополнительно найденный deadlock выхода из групп воспроизведён и исправлен. Финальный QA: **108 tests, 107 pass, 0 fail, 1 skip**; пропущен только opt-in тест настоящего Jamulus. Заключение допускает исправленный код к пилотному выпуску 0.6.0. Browser-проверки, сборки установщиков, backup финального образа и production-проверки координатор завершает отдельно; это заключение не подменяет доказательство этих результатов.

## Подтверждённые замечания

### P1 — запоздавшее чтение возвращает данные после выхода

Место первоначальной находки: `public/app.js`, фоновый `setInterval` чтения `/api/state` и `sessionExpired()`.

Воспроизведение: открыть библиотеку Alice; запустить фоновый GET `/api/state`, задержав его ответ; завершить сеанс; вернуть прежний успешный ответ. Фоновый обработчик выполняет `apply(fresh)`, вновь показывает библиотеку Alice и сохраняет активный указатель офлайн-копии. Это возможно даже после успешного серверного logout: чтение уже было авторизовано до выхода.

Узкая проверка выполнила реальные функции начальной части `public/app.js` и реальный callback фонового таймера в `node:vm`, заменив только сеть, DOM и хранилище. До задержанного ответа: `data:null,user:null`; после: `user.id:"alice"`, песня `PRIVATE A`. Проверка не обращалась к серверу и не меняла данные пользователей.

Необходимое исправление: поколение контекста для чтений и их ошибок; инвалидировать его при выходе и смене аккаунта/группы. Результат чтения применять только к тому контексту, в котором запрос начат. Проверить также `refresh()`, `bootstrap()` и запоздалый 401, способный сбросить уже новый аккаунт.

**Закрыто в коде и регрессиях.** `contextEpoch` учитывается в чтениях, API-ошибках, очереди и ответах сохранения; меняется также при обнаружении новой личности/группы фоновым чтением. Проверены запоздалые ответы после выхода, новый вход после 401, перекрывающиеся фоновые запросы и отказ сети при bootstrap. Семь независимых регрессий находятся в `tests/frontend-session-race.test.mjs`; все проходят. Это тесты реальных функций приложения с управляемым порядком сетевых ответов, а не замена browser-проверки.

### P1 — подтверждение удаления одной группы удаляет другую

Места первоначальной находки: `server/account-lifecycle.mjs:149–163`, `public/account-controls.js:18`.

Воспроизведение: владелец имеет две группы A и B с одинаковым названием; в первой вкладке открывает подтверждение удаления A; во второй переключается на B; в первой вводит название и пароль. Сервер использует активную группу cookie и удаляет B. Аналогичная смена цели возможна для передачи владения и выхода из группы. Проверка текущей сессии под блокировкой защищает от изменения *во время* запроса, но не связывает запрос с показанной пользователю формой.

Узкая проверка выполнила реальные `accountLifecycleHandlers()` и `createAccountGuard()` с тестовым адаптером БД: клиент передал `bandId:"A"`, текущая сессия была в B; получено `status:200`, фактическая цель `DELETE FROM bands` — B. Запрос не обращался к реальной БД.

Необходимое исправление: передавать ожидаемые ID аккаунта/группы, захваченные при открытии формы; проверять их на сервере до действия и после получения транзакционных блокировок. При несовпадении вернуть 409 без изменения данных. Новые опасные операции должны иметь явную цель. Учесть совместимость старых desktop-клиентов отдельно от новых форм.

**Закрыто в коде и финальной API-проверке QA.** Новые формы аккаунта замыкают `X-User-Id` и `X-Band-Id` при открытии. Сервер проверяет ожидаемый контекст в `checkContext()`/`need()`, затем `lockAccount()` повторно проверяет сессию и группу под блокировкой. Общий API и raw-upload также передают контекст; native gateway пробрасывает заголовки. Старые клиенты без заголовков сохранены для совместимости; новые опасные формы существуют только в клиенте с заголовками. Финальный release-набор QA: **12/12**, включая отказ для неверного аккаунта/группы в загрузках, state и logout.

### P2 — deadlock при противоположных выходах из групп

Первоначальный путь: `server/account-lifecycle.mjs`, `/api/bands/leave`. Два музыканта состоят в A/B; один выходит из A, другой из B. Каждый держит `FOR UPDATE` своей группы, затем `UPDATE sessions SET band=next` запрашивает FK-lock противоположной группы. Возникает цикл ожиданий; PostgreSQL откатывает одну операцию, клиент получает 500.

**Закрыто.** Обе группы теперь блокируются в стабильном порядке до изменения сессий. Backend-агент воспроизвёл старое поведение `[200,500]` и проверил исправление `[200,200]` на отдельном сервере 3191 и изолированной БД; три целевые проверки прошли. В `tests/account-lifecycle.test.mjs` добавлен сценарий с временным триггером, создающим управляемое перекрытие только для своих fixture-пользователей. Исходник исправления и теста повторно прочитан в этом ревью; собственный повторный запуск БД не дублировался.

## Проверенные архитектурные свойства

- PostgreSQL остаётся единственной серверной БД. Схема новых действий не вводит внешнюю БД или хранение секретов в клиенте.
- Серверные изменения повторно проверяют действующую сессию и роль после блокировки строк пользователей; операции с несколькими пользователями сортируют полный набор ID. Передача владельца атомарна, уникальный частичный индекс запрещает двух владельцев одной группы.
- Удаление аккаунта запрещено владельцу групп; передача/создание/вступление сериализуются с удалением через строку пользователя. Общие материалы чужих групп сохраняются. Удаление группы ставит файлы в сохраняемую в БД очередь; допустимы только генерируемые UUID, очистка умеет повторяться после ошибок.
- Локальные черновики разделены по аккаунту и группе. Воспроизведение гонки «фоновое чтение — локальная правка — ответ 409 на сохранение» сохранило правку через `restoreLibrary()`; потери черновика в этом сценарии не обнаружено.
- Членский API больше не выдаёт email остальных участников; email своего аккаунта остаётся в профиле. Экспорт профиля не включает чужие профили или библиотеку.
- Аудиобилет привязан к серверной сессии; admission ожидает асинхронную проверку до подключения, затем доступ проверяется периодически. Ретранслятор не заявляет сквозное шифрование или запись потока. Проверка исходников не измеряет задержку реальной группы.
- `/`, `/app`, приглашения и юридические страницы имеют отдельную маршрутизацию; service worker исключает API и установщики из кеша, офлайн-оболочка приложения использует `/app`. Native gateway сохраняет прежний `/` как вход в локальную оболочку.
- Backup останавливает writer, сохраняет PostgreSQL и volume вложений, сверяет состояние БД до/после и возвращает исходное состояние контейнера. Restore check использует новый изолированный проект, проверяет данные, байты, ссылки и доступ UID 1000; удаляет только созданные им ресурсы. Фактический smoke и production backup подтверждаются отдельно DevOps/координатором.

## Документация и границы заключения

Публичные `/privacy` и `/terms` явно обозначены черновиками и не содержат выдуманных реквизитов. Ограничения почтового восстановления, подписи установщиков и физической проверки аудио заявлены, они не переоткрываются этим ревью как новые дефекты.

Строка «Офлайн» в `docs/LEGAL-REVIEW.md` исправлена и соответствует коду: выход блокирует вход в локальную библиотеку, сохраняя черновики и скачанные материалы. Публичная privacy-страница предупреждает об оставшихся локальных данных.

Это техническое заключение не подтверждает юридическую готовность публичного сервиса, запуск на физических Windows/macOS, качественную игру восьми музыкантов или завершённый production deploy. Необходимые доказательства: итоговый QA-набор, проверки исправленных гонок, проверенные Mac/Windows артефакты, backup/restore smoke и отдельный отчёт координатора о production-проверках.
