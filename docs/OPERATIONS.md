# Эксплуатация Psalmony 0.6.0

Psalmony хранит серверные данные только в PostgreSQL 17. База и вложения находятся в отдельных Docker volumes. Ни пересборка приложения, ни обычный откат образа не требуют удаления volumes. Команды ниже выполняются из корня репозитория на том Docker-хосте, где работает нужный Compose-проект.

## Резервная копия

Нужны Bash, Docker Engine с Compose v2 и `sha256sum` либо macOS `shasum`. PostgreSQL должен работать, контейнер приложения должен существовать. Скрипт поддерживает корневой Compose и профиль Екатеринбурга; сервисы должны называться `psalmony` и `postgres`, именованный том вложений должен находиться в `/app/data`.

Локально:

```sh
backup=$(bash scripts/backup.sh --compose-file compose.yaml --output-dir "$PWD/backups")
bash scripts/restore-check.sh --backup "$backup"
```

Екатеринбург:

```sh
backup=$(bash scripts/backup.sh \
  --compose-file deploy/ekaterinburg/compose.yaml \
  --env-file deploy/ekaterinburg/.env \
  --project-name psalmony \
  --output-dir "$PWD/backups")
bash scripts/restore-check.sh --backup "$backup"
```

При дополнительных Compose-файлах повторите `--compose-file` в том же порядке, что при запуске сервиса. Передайте его настоящее имя проекта через `--project-name`, если оно отличается. Скрипт проверяет, что приложение и PostgreSQL относятся к одному проекту. Он не загружает `.env` как shell-код и не печатает окружение контейнеров.

На время дампа приложение недоступно; Caddy может вернуть 502. Скрипт останавливает только исходный контейнер `psalmony`, делает дамп и копирует файловый том. PostgreSQL, proxy и аудиорелей продолжают работать; существующий аудиорелей только читает членство из БД. Не запускайте параллельно обновление, ручной SQL или другой процесс, который пишет в эту БД/том. Другой контейнер с доступом к тому на запись блокирует копирование; снимки таблиц до и после дополнительно обнаруживают изменения БД.

После снимка скрипт запускает тот же контейнер, только если он работал до копирования. Это выполняется и через `trap` при обычной ошибке, SIGINT, SIGTERM или SIGHUP. SIGKILL, падение хоста или Docker не позволяют гарантировать автоматический запуск: после них проверьте `docker compose ... ps` и вручную запустите `psalmony`. Блокировка `/tmp/psalmony-backup-<project>.lock` (на macOS — в `$TMPDIR`) снимается автоматически; после аварийного завершения удаляйте её только убедившись, что другого копирования нет.

Успешная команда печатает путь к новому каталогу `backup-<UTC>-<random>`. Права создаваемых каталогов/файлов ограничены `umask 077`. Каталог содержит:

| Файл | Содержимое |
| --- | --- |
| `database.dump` | `pg_dump --format=custom --no-owner --no-acl` |
| `attachments.tar.gz` | весь `/app/data`, включая оригинальные владельцев и права |
| `database-inventory.jsonl` | число строк и отпечаток содержимого каждой public-таблицы |
| `file-references.tsv` | ссылки БД на вложения/изображения и ожидаемые размеры |
| `files.sha256` | SHA-256 всех файлов тома |
| `manifest.json` | UTC, проект, версия PostgreSQL, ID образов, исходный том и состояние приложения |
| `SHA256SUMS` | SHA-256 всех перечисленных файлов |

Каталоги `.incomplete-*` означают неудачную попытку и не принимаются проверкой восстановления. Не используйте их как резервные копии. Исправьте причину и повторите копирование; оно создаст новый каталог.

Дамп содержит личные данные, хеши паролей и сессии. Держите копии вне Git, с доступом только операторам, и переносите на отдельное защищённое хранилище. Скрипт не шифрует архивы и не удаляет старые копии. SHA-256 обнаруживает повреждения, но не доказывает происхождение: восстанавливайте только доверенные копии. `.env`, TLS-ключи Caddy, установщики, исходники и Docker-образы не входят в этот архив. Секреты и конфигурацию храните отдельно в защищённом хранилище; нужный исходный код и образы сохраняйте для отката.

## Что подтверждает проверка восстановления

`restore-check.sh` не принимает URL рабочей БД, имя рабочего тома или рабочий Compose. Он создаёт уникальный проект `psalmony-restore-*`, два новых тома и PostgreSQL с `network_mode: none`, без открытых портов. Требуется локально доступный образ `postgres:17-alpine` (`docker pull postgres:17-alpine`, если его ещё нет).

Сначала проверяются контрольные суммы. Затем выполняются настоящий `pg_restore` в новую пустую БД и распаковка вложений. Сверяются содержимое и число строк всех public-таблиц, ссылки на файлы, SHA-256 каждого файла, размеры файлов из БД, чтение и создание файлов от UID 1000. Специальные файлы, ссылки и пути с выходом за пределы архива отвергаются. После успеха или ошибки удаляются только ресурсы этого сгенерированного проекта, включая его два тестовых тома. Восстановленные данные не публикуются в сеть.

Успех заканчивается `RESTORE CHECK PASSED`. Проверка доказывает восстановимость БД/файлов, но не запуск конкретного нового приложения, работу почты, HTTPS, установщиков или физических аудиоустройств.

Воспроизводимая разработческая проверка, полностью в новых Docker-ресурсах:

```sh
docker build --tag psalmony-backup-fixture .
bash scripts/backup-smoke.sh psalmony-backup-fixture
```

Она проверяет копию с данными и вложениями, настоящее восстановление, сохранность всех строк и файлов после полного пересоздания контейнера приложения, сохранение исходного running/stopped-состояния приложения, запуск после ошибки копирования, отказ при повреждении архива и очистку временных ресурсов при ошибке уже после восстановления БД. CI запускает её после синтаксических и unit-проверок. Полные API-тесты требуют отдельного сервера с `TEST_BASE`, `IDENTITY_TEST_BASE` и согласованным `DATABASE_URL`; не запускайте их на production.

### Проверено 11 октября 2026 года

Команда `bash scripts/backup-smoke.sh psalmony-psalmony:latest` выполнена на финальном образе 0.6.0 `sha256:b79bda6e24723f16cddde2349247f713fd7d7834131c546e4e68309f9c7119ba` с PostgreSQL 17. Проверка прошла без ошибок:

- Настоящий `pg_restore` восстановил **13 таблиц и 2 вложения**; содержимое таблиц, SHA-256 файлов, ссылки и размеры из БД совпали. UID 1000 читает вложения и создаёт файлы.
- `--force-recreate` заменил только тестовый контейнер приложения. Новый контейнер стал healthy; содержимое всех таблиц и вложений после пересоздания совпало со снимком.
- Работающее приложение запускается после копирования и после ошибки; изначально остановленное приложение остаётся остановленным.
- Повреждённый архив отвергается до восстановления; несоответствие снимка БД после восстановления вызывает ошибку и удаляет созданные проверкой контейнеры и тома.
- Временные проекты проверки удалены. Рабочая локальная PostgreSQL на 54329, приложение на 3180 и QA-сервер на 3190 не использовались и не перезапускались этими проверками.

Это локальное доказательство backup/restore и persistence конкретного образа. Production-копия и проверка после развёртывания выполняются отдельно; результат GitHub Actions этим запуском не подтверждается.

## Обновление и проверка после развёртывания

1. Сверьте адрес хоста, имя проекта и действующие тома. Сохраните копию конфигурации и секретов отдельно, не выводя их содержимое. Зафиксируйте прежнюю версию и ID образов (`docker compose ... images -q psalmony audio`); сохраните образ приложения под уникальным rollback-тегом и при необходимости `docker image save`. Оставьте прежний исходный код доступным.
2. Выполните согласованную копию и `restore-check.sh`. Не продолжайте при ошибке. Отметьте время копии: возврат к ней потеряет более поздние изменения, поэтому при таком откате потребуется отдельное решение.
3. Подготовьте новые файлы приложения и установщиков. Сохраните действующие `.env`, имя проекта и volumes. Не меняйте пароль PostgreSQL только редактированием `.env`: пароль уже созданной роли от этого не изменится.
4. Соберите образ и обновите только приложение/relay, не пересоздавая БД без необходимости:

```sh
docker compose -f deploy/ekaterinburg/compose.yaml --env-file deploy/ekaterinburg/.env build psalmony audio
docker compose -f deploy/ekaterinburg/compose.yaml --env-file deploy/ekaterinburg/.env up -d --no-deps psalmony audio
docker compose -f deploy/ekaterinburg/compose.yaml --env-file deploy/ekaterinburg/.env ps
curl --fail --silent --show-error https://psalmony.91.226.80.181.sslip.io/api/health
```

5. Health должен вернуть `ok: true`, `database: "postgresql"` и ожидаемую версию `0.6.0`. Проверьте содержимое страницы `/`, оболочки `/app`, справки и доступность реально размещённых установщиков. Сверьте SHA-256 установщиков с локальными артефактами.
6. Убедитесь, что `/api/state` без сессии возвращает 401. В разрешённом тестовом аккаунте проверьте вход, список групп, чтение библиотеки и одного вложения, сохранение правки с верной ревизией и отказ устаревшей ревизии. Сверьте данные после повторного запуска приложения. Не создавайте тестовые пользовательские данные в рабочей группе без согласованного пилота.
7. Проверьте последние ошибки приложения/БД и состояние proxy. Успешный health не заменяет эти проверки. Установщики без подписи и сетевое аудио остаются пилотом; при отсутствии физической проверки это явно указывается в отчёте.

## Откат

Если новая версия не прошла проверки, сначала ограничьте запись пользователей. Сохраните отдельную копию текущего состояния, если записи после обновления уже возможны. Не накатывайте старый дамп поверх действующих томов.

**Откат только приложения** допустим после проверки совместимости прежнего кода с текущей схемой/данными. Примените небольшой Compose override с `image: <сохранённый-rollback-тег>` для `psalmony` и `audio`, `pull_policy: never`, затем запустите `up -d --no-build --no-deps psalmony audio` с теми же базовым Compose, `.env` и project name. Повторите health, авторизацию и чтение данных. Сохранённый образ и исходники предпочтительнее новой сборки старого кода с изменившимися зависимостями.

**Восстановление данных** — отдельная контролируемая операция. Сначала повторите `restore-check.sh`. Затем разверните восстановление на новом изолированном Docker-хосте либо в новом Compose-проекте с новым именем и двумя новыми volumes, без `external:` и явных `name:`, без публичных портов и подключения к рабочей БД. Создайте PostgreSQL 17, загрузите `database.dump` через `pg_restore --exit-on-error --single-transaction --no-owner --no-acl`, распакуйте `attachments.tar.gz` в новый том, сохранив UID/GID/права. Запустите подходящий образ приложения только с этими новыми ресурсами. Принципы и команды безопасного создания/проверки представлены в `scripts/restore-check.sh`; его временные ресурсы после проверки не сохраняются.

Перед переключением трафика сравните объём/содержимое данных и файлы, проверьте вход, доступ разных ролей, сохранение и ревизии. Определите судьбу изменений после времени копии и учтите удаления аккаунтов/групп, произошедшие позднее: восстановление старого дампа может вернуть ранее удалённые данные и старые сессии. Переключайте трафик только после принятия этой точки восстановления. Старые рабочие volumes сохраняйте отдельно до завершения проверки и согласованного срока хранения. Ни восстановление, ни откат не требуют `docker volume prune` или удаления томов рабочего проекта.
